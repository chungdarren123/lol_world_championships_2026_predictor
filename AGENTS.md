# Project purpose and agreed constraints

- This is a beginner machine-learning learning project. Teach concepts, explain alternatives and their pros and cons, and connect implementation choices to the learning objective.
- Discuss major architecture and modeling decisions with the user before implementing them. Prefer small, understandable increments with inspectable intermediate results.
- Use regional and international professional tournament data only. Exclude solo queue and ranked-player API data.
- The main forecast is now after the Worlds 2026 Swiss Round 1 draw, conditional on the known Swiss field and opening pairings. Verify and record the precise forecast freeze in UTC before building the revised dataset. Preserve the original pre-Play-Ins audit/configuration as a separate historical artifact.
- Include completed Worlds 2026 Play-In games whose results were available before the new forecast freeze. Exclude subsequent results, including all Swiss and knockout results, from model fitting, feature construction, tuning, and calibration. Keep retrospective evaluation separate.
- Distinguish a historical match date from when its data became available. Disclose uncertainty if reconstructing an authentic pre-tournament snapshot from subsequently downloaded or corrected records.
- Revised modeling direction: a hierarchical Bayesian Bradley-Terry strength model with region and within-region team effects and time decay, feeding a separate Monte Carlo Swiss simulator. Discuss detailed priors, temporal specification, and inference before implementation. Elo is no longer the required primary benchmark; retain earlier diagnostic reports as historical artifacts. Do not introduce notebooks as the implementation interface.
- Use 2026 regional and international professional games plus earlier seasons' international games to inform regional strength. Historical team effects must remain season-specific; never assume an old roster is the current roster. The earlier-season window and historical region mappings require a coverage review. Approved exception: include the 47 LCS/CBLOL promotion games played in 2026 for 2027 league places, preserving their source season. Audit coverage; do not claim complete coverage without evidence.
- Kalshi/Polymarket prices are removed from the project scope; do not use them as priors, fitting targets, or benchmarks.
- Retain games with missing Gold/XP-at-15 values and games across lineup changes. Preserve missing values (never silently replace with zero); track the actual lineups used. Any imputation belongs to a later training pipeline fitted only on training data.
- Include EWC main-event and qualifier games, keeping their event stages distinguishable. Do not treat all EWC games as cross-region main-event matches.
- Canonical identities use reviewed, dated aliases; preserve source IDs. Query region membership as of each game and never use later membership observations as historical evidence. Supplemental LFL membership metadata is permitted for Galions/Solary without importing out-of-pool results.
- Series reconstructed from consecutive game numbers remain provisional. Preserve the known partial Gen.G–Dplus Kia series on 1 August 2026; never fabricate its missing game 1 or treat observed scores as official final scores.
- Initial scope: game-win probabilities, then series results, then tournament outcomes. Champion forecasting is deferred.
- Swiss outputs: advancement and terminal-record probabilities (3-0, 3-1, 3-2, 0-3, 1-3, 2-3), targeting about 100,000 simulations with uncertainty reporting. The top eight by marginal advancement probability are a selection summary, not an observed or necessarily most-probable joint qualifier set. A later knockout simulation must use each simulation's actual qualifiers.
- The user is comfortable with Python; teach machine-learning concepts without assuming they need basic Python instruction.
- Work through GitHub repository chungdarren123/lol_world_championships_2026_predictor. Begin with terminal workflows; eventual output is a deployed, hosted visualization. Hosting platform and frontend framework are not yet selected.
- Commit and push completed, verified checkpoints to GitHub as work progresses; the user has authorized this ongoing workflow. Use meaningful commit messages, run checks appropriate to each change, and describe unresolved scientific limitations honestly. Keep raw data, processed datasets, credentials, and local runtime/model artifacts out of Git. A code checkpoint does not imply that the forecast is ready.
